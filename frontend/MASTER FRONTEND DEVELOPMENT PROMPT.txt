MASTER FRONTEND DEVELOPMENT PROMPT
==================================

PROJECT: DealFlow360
TYPE: Enterprise Deal Operating System / ERP
FRONTEND: React + TypeScript
BACKEND: Node.js + Express + PostgreSQL
AI SERVICE: Python FastAPI
UI: Modern Enterprise ERP / Odoo-inspired, but with completely original branding and UI
ARCHITECTURE: Modular + scalable + API-driven + permission-aware
PRIMARY GOAL: Build a production-ready frontend that can dynamically consume APIs and scale from hackathon MVP to enterprise application.

==================================================
1. CORE PRODUCT VISION
==================================================

Build "DealFlow360" as an intelligent Deal Operating System.

The complete business flow is:

Lead Generation
→ CRM Lead
→ Lead Qualification
→ Operator Contact
→ Customer Conversion
→ 7-Day Trial Subscription
→ Customer Portal
→ Product Selection
→ Quote Generation
→ Product/Category Pricing
→ Discount Negotiation
→ Risk Calculation
→ Team Review
→ Dynamic Approval
→ Customer Negotiation
→ Re-approval if required
→ Quote Confirmation
→ Inventory Check
→ Warehouse Allocation
→ Vendor Selection if stock is insufficient
→ Purchase Order
→ Fulfillment
→ Shiprocket Shipping
→ Invoice
→ Payment
→ Subscription Billing
→ Deal Health
→ Analytics
→ AI/RAG Assistant

The frontend must represent this entire lifecycle.

DO NOT create a collection of disconnected pages.

The frontend must feel like ONE integrated enterprise application.

==================================================
2. IMPORTANT DEVELOPMENT PRINCIPLES
==================================================

DO NOT build static mockup pages.

DO NOT hardcode business logic into UI.

DO NOT hardcode approval results.

DO NOT hardcode discount limits.

DO NOT hardcode risk scores.

DO NOT hardcode inventory.

DO NOT hardcode vendor recommendations.

DO NOT hardcode dashboard numbers.

DO NOT store business data permanently in frontend localStorage.

All business data must come from APIs.

The frontend should work with realistic API responses and loading/error/empty states.

Use mock API adapters only when backend APIs are not yet available.

Every mock must be replaceable with a real API without rewriting the UI.
